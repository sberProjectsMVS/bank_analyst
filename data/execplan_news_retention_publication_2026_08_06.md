# Make the news feed append-only and verify the published landing

This ExecPlan is a living document maintained in accordance with `PLANS.md`.

## Purpose / Big Picture

News that has already appeared on the public landing must remain there even when an upstream page stops listing it. Every command that rebuilds or changes the news landing must also rebuild the public entry page, push it, and verify that the linked GitHub Pages URL serves the newly generated bytes.

## Surprises & Discoveries

- Observation: A successful source refresh was treated as a complete replacement of that source's history.
  Evidence: `scanner/premium_news.py` excluded all previous records whose `source_id` was refreshed before merging the current page.
- Observation: The four-item public decrease matches the raw monitor delta exactly.
  Evidence: the committed cache had 31 records; the current cache has 27, comprising six removals and two additions.
- Observation: The existing `data/premium_changes_cache.json` has 84 records but was only read, never updated by the generator.
  Evidence: `landing/premium_changes.py` defines `_load_changes_cache` but no corresponding write path.
- Observation: Before final publication, the live page showed 86 publications while the latest local generated page showed 87.
  Evidence: a cache-busted request to `https://sberprojectsmvs.github.io/bank_cite/` and `output/sber_vs_banks.html` returned those counts respectively.
- Observation: Several successful pushes remained absent from GitHub Pages; the live response still matched commit `744961c` while `origin/main` had advanced through later commits.
  Evidence: the public response showed 86 publications and an older `Last-Modified` value while the publication repository contained 87 and the new build marker.

## Decision Log

- Decision: Preserve records by stable `record_id` and let fresh observations update matching records without deleting unmatched history.
  Rationale: A source listing is a window into history, not evidence that older news ceased to exist.
  Date/Author: 2026-08-06 / Codex
- Decision: Persist the fully deduplicated combined feed atomically after every successful standalone build.
  Rationale: This protects PBI, editorial, and monitored records uniformly and seeds retention from the known 84-record public cache.
  Date/Author: 2026-08-06 / Codex
- Decision: Treat a landing update as successful only after the configured public URL serves the generated content.
  Rationale: The user consumes only the pushed URL, so a local file or even an unverified push is not the observable outcome.
  Date/Author: 2026-08-06 / Codex
- Decision: Publish `.nojekyll` and cap verification by a fifteen-minute monotonic deadline rather than by a small attempt count.
  Rationale: The deliverable is already final static HTML, so Jekyll adds no value. A real elapsed-time deadline tolerates many fast SSL failures without ending early while still bounding the wait when HTTP requests time out.
  Date/Author: 2026-08-06 / Codex

## Context and Orientation

`scanner/premium_news.py` fetches registered sources and stores normalized records in `data/monitored_premium_news.json`. `landing/premium_changes.py` combines those records with editorial and PremiumBanking.info records. `landing/sber_vs.py` embeds that combined feed into the public comparison page. `publisher.py` copies `output/sber_vs_banks.html` into the sibling `bank_cite` repository and pushes its `main` branch. `main.py` connects those operations to CLI commands.

## Plan of Work

Change the monitor merge so the prior record map is always the base and fresh records only insert or update. Remove the fixed history truncation because it contradicts permanent retention. Add an atomic writer for the combined feed cache and invoke it only after the generated HTML is successfully written. Add a shared workflow in `main.py` that builds the standalone feed first, rebuilds the public comparison page from that feed, and publishes it; use the workflow for news scan, editorial sync, and explicit premium-changes builds. Add public-content verification to `publisher.py`, using a cache-busted request and a bounded retry window. Add focused unit tests for retention, cache persistence, workflow ordering, and publication verification.

## Validation and Acceptance

A test will seed a source with an older record, refresh it with a different current record, and observe both records in the cache. A landing-cache test will build from an older cached record and a new record, then observe both persisted. Publication tests will prove that a mismatched live response is rejected and matching bytes are accepted. The final public page must contain at least the 84 retained records from the existing fail-safe cache and its live bytes must match `output/sber_vs_banks.html`.

## Idempotence and Recovery

All merges are keyed and deduplicated, so repeated scans and builds do not create duplicates. Cache writes use a sibling temporary file followed by an atomic replace. If publication or live verification fails, the CLI exits nonzero and leaves the generated artifact and any already-created publication commit available for a safe retry.
